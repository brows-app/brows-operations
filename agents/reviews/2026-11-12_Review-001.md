## Findings

### #1 [P2] Child registration reads incomplete cancellation state and loses retained tokens [Resolved]

- Status: Resolved.
- Primary location: `source/Brows.Operations/Operations/OperationBase.cs:251-257`.
- Related location: `source/Brows.Operations/Operations/OperationBase.cs:525-539`.
- Problem and trigger: `ValidateChildRegistration` checks only `CancellationRequested` and the live
  `TokenSource`. The batch cancellation helper similarly checks a flag/effective linked token before a
  summary exists. Neither checks whether this operation's original supplied token, or an ancestor's original
  source, already requested cancellation before its link callback has run. A user registration on the supplied
  token can run before the earlier linked-source callback. Calling retained parent progress from that callback
  therefore registers new descendants in a subtree whose supplied token is already canceled.
- Impact: new `Child` work executes and returns `Succeeded`; a new `Children` call enumerates, invokes factories,
  runs work, and returns successful results. This concerns newly submitted work and returned results after
  cancellation was requested, rather than how quickly already-running cooperative delegates stop.
- Further manifestation: after finalization clears `TokenSource`, retained progress for a supplied-canceled
  parent throws `InvalidOperationException` instead of cancellation. For a root canceled through `Cancel()`,
  it throws `OperationCanceledException` with `default`, an uncanceled token, rather than the saved operation
  token. The frozen summary already retains the necessary state, but this registration gate ignores it.
- Evidence: an isolated net10.0 probe started a child parent with an external supplied token, registered a
  later external-token callback inside its delegate, and called both public APIs from that callback.
  It printed:

  ```text
  window: external canceled=True, linked canceled=False
  window: late Child=Succeeded, delegate ran=True, late Children=Succeeded, factories=1
  snapshot: root Child token matches=False, thrown token canceled=False, thrown token default=True
  snapshot: supplied-canceled parent Child threw=InvalidOperationException
  ```

  The callback ordering is deterministic in the exercised runtime; the source was already canceled before
  either new call. The parent delegate was kept running with an explicit task signal. Separate retained-progress
  probes awaited parent completion before making the late calls. No timing-dependent sleep was required.
- Plan alignment: `Plan.md:96-109`, `Plan.md:115-120`, and `Plan.md:234-236` require cancellation-aware
  registration, ambient cancellation propagation, and token retention independent of source disposal.
- Suggested resolution: use one synchronized cancellation-state/token-selection helper for registration and
  batch checks. Account for original supplied/ancestor cancellation before linked callbacks finish, and use
  retained terminal state after disposal. Keep commitment under the existing gate and preserve frozen outcomes
  for completed work. Propagate a canceled token representing the applicable parent/supplied cancellation.
- Resolution: a single synchronized cancellation-state selector now checks frozen summaries first, the current
  effective token, and then original supplied/ancestor sources for the blocked-link window. Registration, batch
  cancellation, and terminal freezing use that state. Frozen successful outcomes remain authoritative after
  later cancellation.
- Fix-phase verification: `ChildRegistration_ObservesSuppliedCancellationBeforeLinkedCallbacks` covers both
  policies and both APIs; `CompletedSuppliedCanceledParent_ChildAndBatchRetainCancellationToken` checks retained
  effective-token identity; `Child_AncestorSuppliedCancellationFreezesBeforeLinkedCallbacks` covers nested ambient
  cancellation before link delivery; and `Child_ResultUsesFrozenCancellationStateBeforeCompletedNotification`
  retains successful outcomes after later cancellation. The focused net10.0 issue suite passed.

### #2 [P2] Supplied-token cancellation bypasses the leases protecting active callbacks [Resolved]

- Status: Resolved.
- Primary location: `source/Brows.Operations/Operations/OperationBase.cs:969-975`.
- Related locations: `source/Brows.Operations/Operations/OperationBase.cs:1098-1111` and
  `source/Brows.Operations/Operations/OperationBase.cs:1347-1356`.
- Problem and trigger: the new supplied token cancels the linked source directly through
  `CreateLinkedTokenSource`. Only `Operation.Cancel()` acquires the tree's cancellation leases. If a callback
  on the effective child token completes the delegate task inline, child finalization runs inside that active
  callback with `TokenSourceCancellationCount == 0` and disposes the source immediately.
- Impact: a callback still executing on a library-owned token observes premature disposal. Accessing
  `childToken.WaitHandle` after completing its work signal throws `ObjectDisposedException`. An uncaught
  exception from such callback code also escapes the caller canceling the external supplied source.
- Evidence: the isolated probe used an ordinary `TaskCompletionSource` without
  `RunContinuationsAsynchronously`; the child returned its task. Its cancellation callback called
  `SetResult()`, confirmed the child had completed, and accessed the callback token's `WaitHandle`.
  With otherwise identical callback/delegate code, the existing root-cancel control and new supplied-token path
  printed:

  ```text
  lease: supplied=False, child complete inside callback=True, callback token access=success
  lease: supplied=True, child complete inside callback=True, callback token access=ObjectDisposedException
  ```

  This isolates the missing lease on the new entry path. Tests using asynchronous completion signals alone
  do not exercise this inline-completion ordering. The old root path's lease remains held until the callback
  returns, then releases/disposes normally.
- Plan alignment: `Plan.md:109` explicitly preserves source-disposal cancellation leases; `Plan.md:200-203`
  requires source release under those leases. The acceptance cases in `Plan.md:285-286` include their correctness.
- Suggested resolution: route cancellation propagated from supplied tokens through ownership-aware machinery
  that acquires/releases the required leases, or otherwise defer disposal until callbacks using each linked
  source have unwound. Apply the same protection through descendants without changing external callback-error
  propagation or canceling unrelated siblings.
- Resolution: supplied tokens now use explicit non-context-flowing relay registrations. Each relay acquires its own
  source lease, calls cancellation outside the state gate, and releases the lease after callbacks unwind. Root
  tree cancellation also cancels each captured source while its independent tree lease is held, so a relay already
  in progress cannot suppress cancellation of an unreached descendant source. Link registrations remain until the
  source is actually disposed.
- Fix-phase verification: `ChildOrBatch_SuppliedCancellationLeasesInlineDescendantCallbacks` covers inline
  completion from both APIs and descendant token callbacks; `SuppliedAndRootCancellation_KeepIndependentCallbackLeases`
  covers concurrent callback leases; and `SuppliedAndRootCancellation_CancelsDescendantBeforeUnreachedRelayDisposal`
  proved the previously missed ordering red before the per-source fix and passed afterward. Existing sibling
  isolation/callback tests remain green. The focused net10.0 issue suite passed.

### #3 [P2] A throwing cancellation notification prevents cancellation and strands leases [Resolved]

- Status: Resolved; **pre-existing at the merge-base**, retained within the plan's cleanup acceptance scope.
- Location: `source/Brows.Operations/Operations/OperationBase.cs:1355-1356`.
- Problem and trigger: `Cancel()` marks cancellation and acquires source leases inside `Synchronization.Update`.
  `Update` then drains `Canceling`/capability notifications before returning. A throwing property subscriber or
  `CanCancelChanged` subscriber prevents execution from reaching `CancelTokenSource`, so actual source
  cancellation and every matching lease release are skipped.
- Impact: the root reports `Canceling == true` while its operation token remains uncanceled. Another `Cancel()`
  sees the flag and cannot recover the request. A delegate waiting for cancellation can therefore remain running
  indefinitely. If work later completes independently, the outstanding lease leaves source disposal pending.
- Evidence: a probe subscribed to the root's `Canceling` property notification, threw an `IOException`, caught it
  at the `Cancel()` caller, and retried cancellation. It then completed the delegate through a separate signal.
  Reflection was used only to inspect private lease state. Observed output:

  ```text
  notification: Canceling=True, operation token canceled=False, active leases=1, completion=False
  notification: after release complete=True, disposal pending=True, active leases=1
  ```

  The token state and leaked lease were observed directly. Indefinite waiting for a delegate that depends solely
  on that token is the execution-trace consequence; the probe used a release signal to finish safely. Comparing
  the baseline confirms the same unguarded update-then-cancel control flow already exists there.
- Plan alignment: `Plan.md:109`, `Plan.md:188-203`, and `Plan.md:285-286` require notification-safe cleanup and
  correct cancellation leases. The allowance for out-of-band `Cancel()` callback exceptions does not require
  attaching this exception to child completion; preserving caller-facing propagation is compatible with
  guaranteeing that committed cancellation/lease work still runs.
- Suggested resolution: retain the notification failure while guaranteeing cancellation and release of every
  acquired lease after the update attempt. If actual token callbacks also fail, preserve both failures with
  the existing distinct infrastructure aggregation machinery. Keep subscriber dispatch fail-fast.
- Resolution: `Cancel()` captures notification failure, attempts cancellation on every captured source, and releases
  every acquired lease even when callbacks or disposal fail. Callback leaves are combined with notification errors
  without retaining the library-created aggregate wrapper. Infrastructure provenance is marked before rethrow, while
  handled out-of-band errors do not enter the node's completion failure list.
- Fix-phase verification: `Cancel_NotificationFailureStillCancelsAndReleasesEveryTreeLease` checks notification-only,
  distinct notification/callback errors, and the same exception instance from both paths, with direct original leaves
  and all source/lease states asserted. `Cancel_NotificationCancellationFailurePreservesInfrastructureProvenance`
  covers handled and unhandled subscriber `OperationCanceledException` paths. The focused net10.0 issue suite passed.

- Fix-phase verification: the corrected worker example compiled against the built net10.0 core assembly with 0
