## Findings

### #1 [P2] Forwarding a failed batch snapshots and scans the child list once per failure [Resolved]

- Status: Resolved.
- Location: `source/Brows.Operations/Operations/OperationBase.cs:406-408`.
- Related locations: `OperationBase.cs:323-325`, `OperationBase.cs:364-366`, and
  `source/Brows.Operations/Operations/OperationBaseCollection.cs:12-13,30-31`.
- Problem and trigger: a delegate awaits or returns `Children(..., OperationFailureBehavior.Throw, default)`
  without handling the resulting failure. For N distinct failing siblings, the public boundary produces a
  library aggregate containing N failures. The enclosing operation's `RecordFailure` expands it and invokes
  `RecordOrdinaryFailure` N times. Each invocation calls `IsFailureInDescendants`, which snapshots every
  child through `ChildCollection.ToArray()` and scans finalized child summaries to locate that exception.
  The collection enumerator first snapshots its underlying list, and LINQ then materializes it again.
  Even though all failures are already recorded, this performs O(N^2) reference copying and membership work.
- Impact: a broad failing batch creates substantial transient allocation and delays parent completion after
  the child work has finished. Synchronous startup/finalization can execute this on the calling UI thread.
  This overhead also occurs with a non-async delegate returning the batch task directly.
- Evidence: the isolated diagnostic workload creates N synchronous failing children with distinct,
  preallocated exceptions, using the public `Children` API. It compares Record and Throw with identical
  leaf trees. A counter/timestamp is captured immediately after `Children` returns its task; the measured
  tail therefore includes enclosing-operation capture/finalization, excluding child creation/work.
  All operations completed synchronously on the measuring thread.

  | Failing siblings | Record tail allocated bytes | Throw tail allocated bytes | Throw tail ms |
  | ---: | ---: | ---: | ---: |
  | 1,000 | 164,744 | 36,529,688 | 24.29 |
  | 2,000 | 334,184 | 145,030,211 | 43.33 |
  | 4,000 | 510,912 | 577,455,792 | 181.49 |
  | 8,000 | 1,032,840 | 2,306,926,480 | 800.81 |

  At 8,000 siblings the complete Record workload allocated 74,146,408 bytes and took 52.33 ms;
  Throw allocated 2,380,558,752 bytes and took 852.73 ms. Record tail time was 0.96 ms.
  These are cumulative current-thread allocated bytes, not retained/live memory.
  Doubling N approximately quadruples Throw tail allocation, corroborating the source trace.
  The merge-base has no library-aggregate replay or per-failure descendant-membership scan; this is introduced
  by the branch. The two policies are a same-revision control, not a measured old-versus-new binary comparison.
- Suggested resolution: determine completed-descendant failure membership once per capture/aggregation phase,
  using a reference-identity set or equivalent index, and reuse that for all forwarded entries. Avoid taking
  a complete child snapshot per exception. Preserve node-local failures, registration ordering, and the rule
  that reusing an exception in an independent sibling still records that sibling's failure.
- Verification: repeat the distinct-failure batch at increasing N and verify near-linear aggregation allocation
  and work. Keep the existing identity/order/independent-sibling and nested-Throw regressions passing.
  Catching the public failure inside the delegate is a practical workaround for this enclosing replay path.
- Resolution: `OperationBase.CaptureWorkFailures` now shares a lazily built reference-identity set across all
  ordinary failures captured from one delegate task. It indexes terminal descendant failures once and discards
  the set at the end of that capture phase. This handles both a library aggregate from `Children(..., Throw)`
  and multiple direct child failures from `Task.WhenAll(... progress.Child(..., Throw))`; node-local failures
  absent from the set are still recorded. Cancellation and infrastructure checks are unchanged.
- Regression verification: `Children_ThrowFailureCaptureAllocationsScaleLinearly` and
  `Child_ThrowTaskWhenAllFailureCaptureAllocationsScaleLinearly` failed before the production fix at
  512-to-1,024 failures, with tail allocation increasing from 9,707,648 to 38,289,320 bytes (batch) and from
  9,906,336 to 38,682,568 bytes (`Task.WhenAll`). After the fix, both pass on net8.0 and net10.0. Each test
  also checks synchronous completion, root failure state, and original child-error identities in source order.
- Scaling verification: the isolated post-fix probe in `out/review-performance-002-fix/results.txt` measured
  tail allocated bytes after child setup on .NET 10.0.15:

  | Failing children | `Children(..., Throw)` | `Task.WhenAll` + `Child(..., Throw)` |
  | ---: | ---: | ---: |
  | 1,000 | 327,000 | 703,200 |
  | 2,000 | 665,472 | 1,418,080 |
  | 4,000 | 1,018,264 | 2,523,624 |
  | 8,000 | 2,060,517 | 5,071,608 |

- Full validation: restore succeeded with NU1900 vulnerability-feed warnings. The Release solution build passed

### #2 [P2] Cancellation rebuilds the entire aggregate for each callback error [Resolved]

- Status: Resolved.
- Original location (reviewed target): `source/Brows.Operations/Operations/OperationBase.cs:1545-1550`.
- Related original location:
  `source/Brows.Operations/Operations/OperationInfrastructureAggregateException.cs:32-41`.
- Problem and trigger: one Canceling notification throws, and cancellation callbacks produce K distinct errors.
  `Cancel()` correctly preserves the notification failure and still cancels/releases sources. However, it then
  loops over all callback errors, calling `Combine` with the growing aggregate each time. Every call walks,
  hashes, copies, and wraps every previously accumulated leaf. Preserving K errors consequently costs O(K^2).
  The trigger requires the notification failure as well as callback errors; callback-only cancellation
  does not enter this accumulation loop.
- Impact: failure handling adds large transient allocation and synchronous latency to Cancel, including when
  it is invoked from a WPF command. More failing callbacks make cancellation disproportionately expensive
  even after all actual callbacks and lease releases have finished.
- Evidence: a pending root delegate registers K callbacks on its effective token, each throwing a distinct
  preallocated exception. Compare identical roots with and without one throwing Canceling notification.
  Measure only `Cancel()`, then release the delegate. The probe verifies the final combined aggregate has
  exactly K+1 leaves; callback-only cancellation has K.

  | Failing callbacks | Callback-only allocated bytes | Combined allocated bytes | Combined ms |
  | ---: | ---: | ---: | ---: |
  | 1,000 | 910,016 | 59,183,504 | 42.32 |
  | 2,000 | 1,815,240 | 228,864,032 | 55.90 |
  | 4,000 | 3,625,616 | 896,483,419 | 224.62 |
  | 8,000 | 7,758,296 | 3,608,016,107 | 1,142.08 |

  Callback-only cancellation at 8,000 callbacks took 29.19 ms.
  The approximately fourfold allocation increase per doubling agrees with the repeated immutable-aggregate
  construction. These are cumulative current-thread allocation measurements, not retained memory.
  The merge-base did not have this combination loop; this is a new cost in the branch's
  notification-safe cancellation path. Restoring the old early exit would reintroduce its cancellation bug.
- Suggested resolution: accumulate the notification failure and callback leaves, then perform one
  reference-based flatten/deduplication and immutable aggregate construction. Preserve notification-first
  ordering, original exception/dispatch information, infrastructure provenance, single-exception identity,
  and guaranteed cancellation/lease release.
- Verification: retain the existing notification-plus-callback and reused-exception regressions, add a
  many-distinct-callback workload, and confirm aggregate construction scales approximately linearly.
  A notification subscriber that handles its own failure avoids this particular combined-error path.
- Resolution: `OperationBase.Cancel` at `OperationBase.cs:1556-1559` now collects callback failure dispatch
  information and combines it with the notification failure once. The new overload at
  `OperationInfrastructureAggregateException.cs:46-55` accepts the remaining dispatch sequence, expands internal
  infrastructure aggregates, deduplicates by exception reference in first-seen order, and freezes one result. It
  returns the original dispatch information when one distinct failure remains. The existing two-dispatch overload
  retains its behavior. The callback-only path and `CancelTokenSource` cancellation and lease-release behavior
  remain unchanged.
- Regression verification: `Cancel_NotificationFailureAggregationAllocationsScaleLinearly` failed before the fix
  at 256-to-512 callbacks (4,396,896 to 16,303,272 bytes; 3.71x) and passed after it. The focused net10.0 run
  passed 10 tests, including `Cancel_CallbackFailuresWithoutNotificationFailureKeepsFlattenedAggregateShape`,
  `Cancel_NotificationFailureStillCancelsAndReleasesEveryTreeLease`, and the three
  `OperationInfrastructureAggregateExceptionTest` cases for typed aggregate expansion, reference deduplication,
  original ordering/EDI preservation, opaque user aggregates, and single-dispatch identity.
- Scaling verification: the isolated probe in `out/review-performance-002-issue2/` used one warmup and three
  measured repetitions on .NET 10.0.15, workstation GC, and 16 reported processors. It measured cumulative
  current-thread allocated bytes around synchronous `Cancel()` only; values are not retained memory.

  | Failing callbacks | Callback-only allocated bytes | Combined allocated bytes | Combined ms |
  | ---: | ---: | ---: | ---: |
  | 1,000 | 910,483 | 1,273,944 | 3.46 |
  | 2,000 | 1,815,240 | 2,558,848 | 8.46 |
  | 4,000 | 3,625,616 | 4,739,600 | 14.07 |
  | 8,000 | 7,267,928 | 9,505,176 | 29.97 |

  Combined allocation now grows approximately linearly as callback count doubles, compared with the original
  59,183,504 / 228,864,032 / 896,483,419 / 3,608,016,107 bytes. Probe command:
  `dotnet run --project out/review-performance-002-issue2/Probe.csproj --configuration Release --no-restore`.
- Full validation: `dotnet restore` succeeded with NU1900 warnings because NuGet.org and the configured GitHub
  vulnerability feeds were unavailable. `dotnet build --no-restore --configuration Release` passed with 0 errors
  and 60 feed warnings. `dotnet test --no-build --no-restore --configuration Release` passed core tests 228 on

  net8.0-windows, and net10.0-windows. Composition test projects reported no tests discovered. All three source
  package projects packed successfully with the same vulnerability-feed warnings.
