## Findings

### #1 [P2] Preserve callback failure propagation when aggregate flattening yields no leaves [Resolved]

- Status: Resolved.
- Location: `source/Brows.Operations/Operations/OperationBase.cs:296-297` (target revision).
- Related locations: `OperationBase.cs:284-286` and
  `source/Brows.Operations.Windows/Windows/Data/OperationCommandConverter.cs:64-70`.
- Problem and trigger: an operation-token callback throws a valid empty `AggregateException`, for example
  `token.Register(() => throw new AggregateException("callback failed"))`. `CancellationTokenSource.Cancel()`
  wraps that callback failure in an aggregate. The new helper flattens it and adds only its inner leaves to
  `failures`; an empty aggregate contributes none. If no other callback or lease-release error contributes a leaf,
  `failures.Count` remains zero and the operation's `Cancel()` returns normally. The same problem applies to a
  descendant callback reached through root cancellation and to aggregates containing only empty aggregates.
- Impact: a real callback failure disappears at the cancellation boundary. Callers cannot handle it, and the WPF
  Cancel command's existing aggregate-exception logging path is bypassed. Actual token cancellation and cleanup
  can succeed; the defect concerns lost exceptional propagation, not a claim that cancellation itself is skipped.
- Evidence: an isolated probe against the freshly built target assembly registers one callback, keeps its delegate
  pending with an explicit task signal, invokes cancellation, records the exception, then releases/joins work.
  The callback executes exactly once in every row:

  | Entry path | Effective token canceled | Exception received by caller |
  | --- | --- | --- |
  | Root Cancel, callback on root token | True | None |
  | Root Cancel, callback on child token | True | None |
  | Supplied-token cancellation, same child callback | True | AggregateException |

  A direct CancellationTokenSource control also throws AggregateException for the same callback. Reflection in
  the operation probes only constructs/starts the internal root and invokes its existing Cancel/Completion members;
  callback registration uses the delegate's token. No timing-dependent sleep is required.
  Baseline source comparison confirms this is introduced by the branch: its catch unconditionally executes
  `throw new AggregateException(..., ex).Flatten()`, which remains exceptional even with zero flattened leaves.
  The baseline binary was not rebuilt. Dropping empty nested wrappers while other leaves still cause an exception
  was already possible with Flatten and is not a separate new finding here.
- Suggested resolution: retain whether any cancellation callback threw independently of the flattened leaf count.
  Preserve exceptional propagation when the resulting list is empty, while still canceling every captured source
  and releasing all leases. Keep the existing callback-only AggregateException shape and the efficient combined
  notification/callback path.
- Resolution: `CancelTokenSource` records whether any cancellation source raised an `AggregateException` separately
  from the flattened leaf count. It now throws the existing flattened callback-failure wrapper when that list is
  empty, after all captured sources have been canceled and all leases released. Mixed empty/nonempty flattening and
  notification exception identity keep their existing behavior. Current fix:
  `source/Brows.Operations/Operations/OperationBase.cs:251,285,298`.
- Verification: `OperationBaseTest.Cancel_EmptyAggregateCallbackFailureStillPropagatesAndReleasesEveryTreeLease`
  covers root and child callbacks throwing empty and nested-empty aggregates. The five cases assert callback-only
  propagation and wrapper shape, cancellation of all three operation tokens, callback invocation, work completion,
  lease release, and token-source disposal. The notification-plus-empty-callback case retains the original
  notification exception instance. Test: `tests/Brows.Operations.Tests/Operations/OperationBaseTest.cs:1058`.
- Red/green evidence: before the fix, the focused run failed in all four callback-only cases because `Cancel()`
  returned normally; the notification-plus-callback case passed. After the fix, the same focused run passed **5/5**.
  The related cancellation fixture passed **12/12**, including ordinary callback aggregation and allocation scaling.
