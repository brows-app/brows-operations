## Findings

### #1 [P2] Timeouts and other foreign canceled tokens are reported as cancellation, hiding the failure [Resolved]

- Status: Resolved
- Location: `source/Brows.Operations/Operations/OperationBase.cs:359-367` (target revision); documented in
  `source/Brows.Operations/Operations/IOperator.cs:43-46` and `Plan.md:92-95`
- Problem and trigger: `RecordFailure` treats any newly observed `OperationCanceledException` as cancellation when
  the exception's own token is canceled. This applies even when that token has no relationship to the operation
  tree. A delegate that times out triggers this rule. Examples are `new CancellationTokenSource(timeout)` or
  `CancelAfter` used locally, and `HttpClient.Timeout`, which throws `TaskCanceledException` carrying its internal
  canceled token. In each case the timeout is recorded as cancellation rather than a failure. Nothing in the
  operation tree requested cancellation.
- Impact:
  - A root that times out completes with `Error == null` and `CompleteWithError == false`. `OperationManager`
    therefore removes it as if it succeeded, and the user never sees the failure.
  - A child under `Record` returns `OperationResultKind.Canceled` instead of `Failed`. Callers that filter on
    `Failed` skip it, as the README example does at `README.md:42`. Callers that treat `Canceled` as "the user
    stopped this" draw the wrong conclusion.
  - Under `Throw`, the caller receives a cancellation instead of the failure.
  - The baseline (`b79aa81`, `Operate`) recorded these exceptions as errors unless the operation token itself was
    canceled. This is therefore a regression in failure visibility.
- Evidence:
  - The existing test `OperatorTests.OperationCanceledExceptionWithCanceledExceptionToken_IsNotRecordedAsAnError`
    (`tests/Brows.Operations.Tests/Operations/OperatorTests.cs:1514-1527`) asserts this behavior for a foreign
    canceled token.
  - A temporary probe on net10.0, since deleted, observed the following.
    - A root delegate awaiting `Task.Delay(Infinite, timeoutCts.Token)` with a 20 ms timeout completed with
      `Error=null`, `CompleteWithError=False`, and the root collection count `0`.
    - The same timeout inside `Child(..., Record, default)` returned `Kind=Canceled` with a
      `TaskCanceledException`.
  - Inference: `HttpClient` timeouts follow the same path because their exception token is a canceled internal
    token.
- Suggested resolution: Classify a new exception as cancellation only when one of these holds:
  - the operation's own linked token is canceled;
  - the parent or supplied token is canceled;
  - the exception's token belongs to the operation tree.

  Tree tokens are the operation tokens and supplied tokens of this node and its descendants. Cancellations
  forwarded from descendants are already recognized through `TreeState.TryGetCancellation` before this fallback
  runs. The fallback therefore does not need to accept arbitrary tokens to meet the goal in `Plan.md:94-95`.
  Update `Plan.md`, the `IOperator` remarks, and the regression test so that a foreign canceled token is recorded
  as a failure.
- Verification: A root that times out on a local `CancellationTokenSource` stays in the collection with
  `CompleteWithError == true`. A `Record` child that times out returns `Failed`. A child canceled through its
  supplied token, or through the parent, still returns or throws cancellation.

Resolution (2026-11-13): The owner confirmed the contract. An operation is canceled only when cancellation was
requested through a token the framework knows about. Cancellation of any other token, including a timeout, is a
failure in roots and in children.

- `source/Brows.Operations/Operations/OperationTreeState.cs:20,34-50` adds a tree-scoped set of known tokens.
  `AddKnownToken` registers a token and `IsKnownCanceledToken` checks it.
- `source/Brows.Operations/Operations/OperationBase.cs` registers each operation token (line 1143), each token
  supplied to `Child` or `Children` (lines 90 and 562), and the batch token.
- Exceptions are classified with the known-token check instead of `CancellationToken.IsCancellationRequested`:
  - delegate failures in `RecordFailure` (lines 360-367);
  - batch enumeration and factory exceptions in `ClassifyBatchException` (lines 748-750);
  - boundary errors in `MarkBoundaryFailure` (lines 877-878).
- A cancellation exception still counts as cancellation when the operation's own linked token is canceled. This
  covers delegates that link their own sources to the operation token.
- A canceled unknown token now gives:
  - a root that keeps the exception as `Error` and stays in the collection;
  - a `Record` child that returns `Failed`;
  - a `Throw` child that propagates the exception as a work failure;
  - a factory or enumerator exception that is a construction error, as for any other factory exception.
- Documentation: `source/Brows.Operations/Operations/IOperator.cs:43-48` and `Plan.md:92-96`, `Plan.md:115-116`
  and `Plan.md:278-279` now state the rule.

Regression evidence (red/green, net10.0 Release, repository root):

- I added these tests:
  - `OperationBaseTest.Child_TimeoutOnUnknownTokenIsAFailure(Record|Throw)`
  - `OperationBaseTest.Children_TimeoutOnUnknownTokenIsAFailedOutcome`
  - `OperationBaseTest.Children_FactoryCancellationOnUnknownTokenIsAnError`
  - `OperatorTests.RootTimeout_IsRecordedAsAnError`
- I replaced `OperatorTests.OperationCanceledExceptionWithCanceledExceptionToken_IsNotRecordedAsAnError` with
  `OperationCanceledExceptionWithUnknownCanceledToken_IsRecordedAsAnError`.
- Before the fix, all six cases failed with the reported behavior: `Canceled` instead of `Failed`, the root
  `Error` null and the root removed, or the factory timeout treated as cancellation. The factory test was rerun
  against the unfixed sources after its assertions were rewritten, and it failed the same way. After the fix, all
  six pass.
- Three existing tests used a private canceled token to stand in for child-only cancellation:
  - `OperationBaseTest.ChildOnlyCancellation_UsesPolicyAndPreservesOriginalException`
  - `OperatorTests.Children_RecordReturnsMixedOutcomesInSourceOrder`
  - `OperatorTests.Children_ThrowUsesFailureAndCancellationPrecedence`

  They now cancel through a supplied grandchild token, using the `CancelThroughSuppliedToken` helper in each

### #2 [P2] Validation, registration, and listener errors escaping a root are no longer displayed [Withdrawn]

- Status: Withdrawn
- Location:
  - `source/Brows.Operations/Operations/OperationBase.cs:343-347`: escaped infrastructure is recorded only as
    infrastructure.
  - `OperationBase.cs:871-882` (`MarkBoundaryFailure`) and `OperationBase.cs:1797-1799`
    (`ProgressWrapper.Change`): where the exceptions are marked.
  - `OperationBase.cs:1266-1267`: `CompleteWithError` ignores infrastructure.
  - `OperationBase.cs:1317` and `OperationBase.cs:1406-1423`: the root fault and its `async void` observer.
  - `source/Brows.Operations/Operations/OperationManager.cs:30-41`: removal of non-relevant roots.
- Problem and trigger: A root delegate lets one of these exceptions escape:
  - a library argument error, for example `progress.Child(name, null, ...)` or `Children` with a null source,
    factory, or child delegate;
  - a late-registration `InvalidOperationException`;
  - an exception thrown by a `PropertyChanged`, `ProgressChanged`, or `TargetChanged` subscriber during
    `progress.Change`.

  Each of these is now marked as infrastructure. The root therefore records no `Error`, sets
  `CompleteWithError = false`, and is not relevant, so `OperationManager` removes it. The root's `Completion`
  then faults, and `ObserveCompletion` rethrows the exception through `async void` on the operator's
  synchronization context.
- Impact:
  - The failed root disappears from `IOperator.Operations` and from the WPF control. This contradicts
    `README.md:100` and `source/Brows.Operations/README.md:5`: "Failed operations remain available with their
    error state until removed."
  - The same exception reaches the context's unhandled-exception path. On a WPF dispatcher, this terminates the
    application unless `DispatcherUnhandledException` handles it. With no context, it is an unhandled thread-pool
    exception, which terminates the process.
  - In the baseline, both kinds of error escaping a delegate went through `RecordFailure`. They set the root's
    `Error` and kept it visible, without any process-level fault.
  - `Plan.md:245-247` deliberately sends these errors to internal completion. It does not address the loss of the
    displayed error or the escalation to a crash.
- Evidence: A temporary probe on net10.0 (since deleted) ran a root delegate that awaited
  `progress.Child("bad", null, Record, default)`. It observed:
  - `Completion` faulted with `ArgumentNullException`;
  - `Error=null`, `CompleteWithError=False`, and the root collection count `0`;
  - the same `ArgumentNullException` delivered to the synchronization context by the `async void` observer.

  Static trace: `RecordFailure` returns at line 345 after `RecordInfrastructure`, before `RecordOrdinaryFailure`
  could set `Error`/`Relevant`. The `Operation_Completed` handler removes the root because `Relevant == false`.
- Suggested resolution: Keep infrastructure precedence at the `Child`/`Children` boundaries, where it serves
  enclosing callers. When a root records an escaped infrastructure failure, also make the failure visible: set
  `Error` if it is null, set `Relevant`, and set `CompleteWithError`. Doing this for every infrastructure failure
  at a root may be simpler. Then either stop rethrowing these failures through `ObserveCompletion`, or limit the
  rethrow to failures that cannot be displayed, such as errors raised while publishing `Complete` itself. Update
  the README sections on failure retention and root behavior to match.
- Verification:
  - A root delegate that lets `ArgumentNullException` from `progress.Child(name, null, ...)` escape remains in the
    collection with `Error` set and `CompleteWithError == true`, and nothing is posted to the context's
    unhandled-exception path.
  - The same holds for a throwing `ProgressChanged` subscriber.
  - `Child`/`Children` callers inside an enclosing delegate still receive these errors as exceptions under either
    policy.

Withdrawn (2026-11-13): The current behavior is by design. The owner confirmed that infrastructure errors should not
occur in practice, and that when one does, rethrowing it on the synchronization context and terminating the app is
the intended way to report it immediately. Root `Completion` faulting and the `async void` observer rethrowing the
error are therefore correct. Losing the root from the collection is accepted because the app is expected to fail.
`Plan.md:245-247` already specifies this. I prototyped a fix that displayed the error on the root and suppressed the
rethrow, then discarded it at the owner's request. No code changed for this issue.

### #3 [P3] README example and docs still use the removed `OperationResult.Outcome` property [Resolved]

- Status: Resolved
- Location:
  - `README.md:42`: compiling code.
  - `README.md:71`, `source/Brows.Operations/README.md:28`,
    `source/Brows.Operations/Operations/IOperationProgress.cs:144`, and `Plan.md:23`: prose and the public
    contract.
- Problem and trigger: `OperationResult` is now `record OperationResult(OperationResultKind Kind, Exception Error)`
  (`source/Brows.Operations/Operations/OperationResult.cs:15`). The getting-started example filters with
  `result.Outcome == OperationResultKind.Failed`. Three other places tell readers to check a result's "Outcome"
  for `Succeeded`: the README prose, the package README, and the `Child` XML remarks.
- Impact: Copying the README example fails with CS1061. The XML documentation shown in IntelliSense, and the
  package README, name a property that does not exist.
- Evidence: `grep -n Outcome` over the target finds these references. The sample app was already migrated
  (`samples/Brows.Operations.Sample/OperationsSampleWindow.xaml.cs` uses `result.Kind`). No references to `Outcome`
  remain in the C# code apart from this XML comment.
- Suggested resolution: Replace `result.Outcome` with `result.Kind` in `README.md:42`, and change the prose to
  "whose `Kind` is `OperationResultKind.Succeeded`" in `README.md:71`, `source/Brows.Operations/README.md:28`, and
  `IOperationProgress.cs:144`. Update the positional parameter name at `Plan.md:23` if the plan is kept as a
  reference.
- Verification: `grep -rn "Outcome" README.md source --include=*.md --include=*.cs` returns no property references.
  Pasting the README example into a project that references the package compiles.

Resolution (2026-11-13): The documentation now uses `Kind`. No code or public API changed.

- `README.md:42`: the example filters on `result.Kind`.
- `README.md:71`, `source/Brows.Operations/README.md:28`, and
  `source/Brows.Operations/Operations/IOperationProgress.cs:144` (XML remarks): the prose says "`Kind`" and "a Kind of
  Succeeded".
- `Plan.md:23`: the positional record parameter is `Kind`, matching `OperationResult.cs:15`.

Verification (net8.0 scratch console project outside the repository, referencing `Brows.Operations.csproj`):

- Before the fix, the README line `batch.Results.Where(result => result.Outcome == OperationResultKind.Failed)`
  failed with CS1061 (`'OperationResult' does not contain a definition for 'Outcome'`).
- After the fix, the same line with `result.Kind` builds with 0 warnings and 0 errors.
- `dotnet build -c Release` of the solution succeeded with 0 warnings and 0 errors. The change is documentation
  only, so I did not rerun the test suite. The remaining `Outcome` mentions in `Plan.md` (lines 75 and 114) describe

## Open questions

- `Children` rechecks parent and batch cancellation after joining (`OperationBase.cs:676-685`) and discards the
  results of children that completed. `Child` does not recheck after its join, because it uses the child's
  frozen summary. A parent canceled between a child's freeze and the caller's resumption therefore produces
  `Succeeded` from `Child` but `OperationCanceledException` from `Children`. `Plan.md:119-120` allows the batch
  behavior. Confirm that the asymmetry is intended before treating it as a defect.
- `Child` with an already-canceled supplied token commits the child to the observable collection and starts it.
  The child skips its delegate and completes canceled. `Children` rejects an already-canceled batch token before
  registering anything (`OperationBase.cs:567-570`). Should `Child` also reject before registration, so that no
  canceled placeholder child appears?
