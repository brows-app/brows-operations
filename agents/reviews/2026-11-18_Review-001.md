## Summary

Four findings (three P2, one P3), all resolved. Responsive display could keep a progress bar that exceeds the
viewport and could put operation commands beyond the visible area at narrow widths. The new visibility styles
also affected consumers in Default mode, and the sample stopped short of its last documented layout stage.

## Findings

### #1 [P2] Responsive display underestimates a progress bar styled with scoped resources [Resolved]

- **Status** — Resolved. Repository review #14.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:83-95`.
- **Problem and impact** — The width calculation applies `OperationProgressBarStyle` to a detached
  `ProgressBar` and caches its minimum width and margin. If the style uses a `DynamicResource` resolved
  from the control or its host, the real bar can resolve the resource and the probe falls back to 100 DIP.
  The layout can retain the bar after it runs out of room, forcing horizontal scrolling.
  [WPF resource lookup][wpf-resources]
- **Evidence** — A WPF probe arranged an active operation at 1,250 DIP and used
  `MinWidth="{DynamicResource BarMinimum}"` with `BarMinimum = 300d` in `OperatorControl.Resources`.
  The live bar resolved 300 DIP and stayed visible. The viewport was about 1,233 DIP and the content
  extent reached 1,350 DIP. Updating the resource to 400 DIP grew the extent to 1,450 DIP while the
  same display stage remained active.
- **Suggested resolution** — Resolve the sizing properties in the same resource and binding context
  as the live bars, then reevaluate the stage when those effective values change.
- **Verification** — Use a scoped dynamic minimum width and a viewport between the fallback and actual
  thresholds. Verify the bar collapses, horizontal overflow disappears, and changing the resource to a
  smaller value can restore the bar without replacing the style.
- **Resolution** — The template now contains a collapsed `PART_OperationProgressBarProbe` progress bar
  (`source/Brows.Operations.Windows/Resources/Styles.xaml:450`) that binds `OperationProgressBarStyle` exactly
  as the row bars do, so it resolves the same resources. `OperatorControl` binds the probe's effective
  `MinWidth` and `Margin` into private dependency properties whose change callbacks reevaluate the stage
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:47`, `:131`, `:141`, `:1023`). The
  detached probe, its cache, and the style-change cache reset were removed. Weak binding updates avoid
  value-changed subscriptions that would retain the control.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_ProgressBarMinimumWidthUsesHostResources`
  failed before the fix (bar visible, 67.3 DIP scrollable width at 1,300 DIP with `BarMinimum = 300d`) and
  passes after it: the bar collapses with no horizontal overflow, then reappears without overflow when the
  resource changes to 100 DIP. An implicit `ProgressBar` style case was also tried and dropped: the row bars
  bind `Style`, so implicit progress bar styles never apply to them and the probe matches that behavior.

### #2 [P2] Default display overrides consumer styles for row cells and headers [Resolved]

- **Status** — Resolved. Repository review #15.
- **Location** — `source/Brows.Operations.Windows/Resources/Styles.xaml:37-63`,
  `:295-334`, and `:509-571`.
- **Problem and impact** — The new visibility rules assign explicit styles to five row cells and all
  seven header cells. Those assignments apply in Default mode as well. A consuming app's implicit
  `ContentControl` style used to supply padding, alignment, or a custom template for those cells.
  The new explicit styles replace it, which can break a consumer's formatting on upgrade.
  [WPF style precedence][wpf-precedence]
- **Evidence** — The baseline XAML leaves those `ContentControl.Style` values unset. In a probe with
  an implicit `ContentControl` style setting 13 DIP of padding and Default display, the depth and
  name row cells retained 13 DIP. The data, progress, rate, average, target, and all header cells
  reported zero padding.
- **Suggested resolution** — Apply responsive visibility through the parent template's triggers or
  through wrappers so the original cells can receive their implicit style.
- **Verification** — Verify that a scoped implicit style applies to every column cell and header in
  Default mode. Switch to Responsive mode, resize past each breakpoint, and check that restored
  cells still use the consumer's style.
- **Resolution** — The three explicit cell styles were removed. The data, progress, rate, average, and target
  row cells and all header cells now bind `Visibility` to internal `DataColumnVisibility`,
  `ProgressColumnVisibility`, and `ProgressRateColumnVisibility` properties
  (`source/Brows.Operations.Windows/Resources/Styles.xaml:267-303` and `:491-551`), set with the display stage
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:236`). The cells' `Style` remains
  unset, so implicit styles apply in both modes.
- **Fix verification** — `OperatorControlTests.CellsRetainImplicitConsumerStyle` (Default and Responsive) failed
  before the fix: only the depth and name cells had 13 DIP padding. After the fix, all seven row cells and
  seven header cells have 13 DIP padding and are visible in Default mode and in Responsive mode after
  narrowing to the final stage and widening again.

### #3 [P2] The narrowest responsive stage puts root commands outside the viewport [Resolved]

- **Status** — Resolved. Repository review #16.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:130-136`
  and `source/Brows.Operations.Windows/Resources/Styles.xaml:498-508`.
- **Problem and impact** — The last stage hides the header cells and moves the data values inline.
  The shared Depth, Name, and Command columns still require 400 DIP. A narrow host must scroll
  horizontally to reach the root command. If the host uses the supported scroll viewer style API
  to disable horizontal scrolling, the command can end up entirely outside the viewport. This
  affects Cancel while a root runs and Remove after it fails.
- **Evidence** — At a 320 DIP control width, the probe reached the final stage and measured a
  400 DIP extent with the standard scrollbar policy. With horizontal scrolling disabled via
  `OperationScrollViewerStyle`, the viewport was about 303 DIP, scrollable width was zero, and
  the Cancel button's right edge was still at 400 DIP. The action starts in the fixed command
  column, which begins at 300 DIP.
- **Suggested resolution** — Let the name and depth columns shrink in the final stage, or place the
  root command beneath the row when the viewport cannot fit the remaining columns. Keep both actions
  visible and usable without a horizontal scrollbar in that layout.
- **Verification** — At 320 DIP with horizontal scrolling disabled, verify that Cancel on an active
  operation and Remove on a failed one fit in the viewport and accept pointer input.
- **Resolution** — In the final stage, the header's Name column receives the viewport width remaining beside the
  other visible columns, capped at its declared width, and is reapplied as the viewport changes within that
  stage (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:194` and `:242`). Rows share
  that width, so long names are clipped instead of pushing the command column out. Commands remain in view
  down to the Depth and Command widths, 150 DIP by default. The property remarks and package README describe
  this.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_NarrowViewportKeepsCommandsReachable` failed
  before the fix (both buttons ended at 400 DIP in a 303.7 DIP viewport and hit testing missed them) and passes
  after it: Cancel and Remove lie within the viewport and hit testing at their centers reaches each button.
  `ResponsiveDisplay_RestoresColumnsWhenWidenedOrDisabled` confirms the declared widths return when widened.

### #4 [P3] The sample cannot reach the final responsive stage by resizing [Resolved]

- **Status** — Resolved. Repository review #17.
- **Location** — `samples/Brows.Operations.Sample/OperationsSampleWindow.xaml:6` and
  `samples/Brows.Operations.Sample/README.md:89`.
- **Problem and impact** — The sample limits the window to 900 DIP while moving data beneath the
  operation requires a viewport below roughly 650 DIP. The README tells readers to narrow the
  sample to see that transition, so the shipped demo cannot show the complete sequence.
- **Evidence** — A probe loaded the sample's actual XAML and theme, assigned an active operation,
  and arranged its content at 884 DIP as a check allowing 16 DIP for window chrome. The operation
  viewport was 760 DIP and Data remained in its column. The XAML's fixed horizontal margins and
  padding leave far more than 650 DIP at the minimum window width.
- **Suggested resolution** — Make the demo resizable to a viewport below the final threshold and
  keep the sample controls usable at that width, or revise the README to describe the stages the
  window can actually demonstrate.
- **Verification** — Follow the sample resize steps and check that each documented stage appears.
- **Resolution** — The sample window's `MinWidth` is now 720 DIP
  (`samples/Brows.Operations.Sample/OperationsSampleWindow.xaml:6`), leaving an operation viewport of about
  600 DIP, below the 650 DIP threshold for moving Data beneath an operation. The README text is unchanged
  because the documented sequence is now reachable.
- **Fix verification** — A temporary WPF render loaded the sample's window XAML and theme, assigned a running and
  a failed operation, and rendered 704 DIP of client width (720 DIP less chrome) and 1,424 DIP. At 704 DIP,
  Data, Progress, Rate, Average, and Target appeared beneath each name with the headers hidden and no
  horizontal scrolling. The scenario cards remained readable, with their buttons wrapping one per line. The
  render was removed afterward. The interactive window was not opened.
