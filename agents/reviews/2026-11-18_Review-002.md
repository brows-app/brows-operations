## Findings

### #1 [P2] Default mode forces cells visible when a consumer style hides them [Resolved]

- **Status** — Resolved. Repository review #18.
- **Location** — `source/Brows.Operations.Windows/Resources/Styles.xaml:265-304` and `:489-552`.
- **Problem and impact** — The cell and header templates now bind `Visibility` directly to the responsive
  state. In Default mode the binding supplies `Visible` at template precedence, overriding an implicit
  style's visibility trigger. An app that deliberately hides a header or selected cell values can show
  them after upgrading. Other style properties, such as the padding covered by the existing regression
  test, still apply. [WPF property precedence][wpf-precedence]
- **Evidence** — The baseline leaves cell and header visibility unset. At the target, a scoped implicit
  `ContentControl` style with triggers collapsing `Content="Data"` and `Content="details"` was present on
  both affected controls, yet both remained visible in Default mode. WPF reported `ParentTemplate` as
  the effective value source. A standalone cell using the same style collapsed.
- **Suggested resolution** — Apply responsive hiding to a wrapper or another template element so
  visible column cells and headers can keep the visibility supplied by the consumer.
- **Verification** — Confirm that style-triggered hiding works in Default and at wide Responsive widths,
  and that transitions between responsive stages still hide their intended column cells.
- **Resolution** — The cells no longer set `Visibility`. Row cells and header cells are named, and
  `DataTemplate.Triggers` and `ControlTemplate.Triggers` collapse them only while their values are shown
  beneath the operation (`source/Brows.Operations.Windows/Resources/Styles.xaml:442-460` and `:588-602`).
  An inactive trigger supplies no value, so the consumer's style decides visibility outside those stages. The
  internal column-visibility properties were removed from `OperatorControl`.
- **Fix verification** — `OperatorControlTests.CellsRetainImplicitConsumerVisibility` (Default and Responsive at
  1,400 DIP) failed before the fix with the Data cell and header visible, and passes after it.
  `ResponsiveDisplay_CollapsesInStagesAsWidthDecreases` confirms each stage still collapses its row and header
  cells, and `CellsRetainImplicitConsumerStyle` confirms implicit padding still applies.

### #2 [P2] The progress bar probe misses row-specific sizing and invokes style handlers outside rows

- **Status** — Partially resolved. Row-specific sizing is accepted as a documented limitation. Repository review #19.
- **Location** — `source/Brows.Operations.Windows/Resources/Styles.xaml:448-453` and
  `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:131-152`.
- **Problem and impact** — The collapsed probe uses the style at control level. The real bar binds its
  value to the operation's progress and inherits that operation's data context. A style whose sizing
  depends on the row can therefore keep a bar visible when it exceeds the viewport. The probe also
  loads in Default mode and raises style events even with an empty operation list. In the baseline
  the style was applied only to operation-row bars. [WPF Loaded event][wpf-loaded]
- **Evidence** — A style trigger set `MinWidth=300` at `Value=50`. A half-complete operation's live bar
  took the 300 DIP minimum, while the probe had value and minimum width zero. In a viewport of about
  1,233 DIP the bar stayed visible, producing a 1,350 DIP extent. In a separate probe, a style
  `Loaded` handler fired once for an empty Default-mode control and received the host's data context.
- **Suggested resolution** — Obtain the sizing inputs from the styled operation-row bars so their
  effective properties determine the threshold. Keep consumer style application on the row elements
  to preserve the style's event and data-context behavior.
- **Verification** — Test a minimum-width trigger driven by live progress and check both directions
  of the size change. Verify that an empty Default-mode control raises no row-style load callbacks.
- **Resolution** — The template now has a collapsed `PART_OperationProgressBarProbeHost` decorator
  (`source/Brows.Operations.Windows/Resources/Styles.xaml:471`). `OperatorControl` creates the probe in it
  only in Responsive mode, with `DataContext` explicitly null, and removes it in Default mode and when the
  template changes (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:123`, `:383`, and
  `:1042`). Default mode therefore applies `OperationProgressBarStyle` only to operation rows, as in the
  baseline, and style bindings never see the host's data context.
- **Not changed** — Sizing that depends on an operation's values, such as a trigger on progress, is still not
  reflected. Reading the size from live row bars was not adopted: a collapsed bar's template is never applied,
  so the threshold would rely on cached guesses, and progress-dependent minimum widths are uncommon. The
  `OperationDisplay` remarks and the package README now document this and the single hidden progress bar.
- **Fix verification** — `OperatorControlTests.ProgressBarStyle_IsNotAppliedWithHostDataContext` failed before
  the fix in both modes: a style binding's converter received the `host` data context with no operations. It
  passes after the fix: no conversions in Default mode and none with the host context in Responsive mode.
  `ResponsiveDisplay_ProgressBarMinimumWidthUsesHostResources` and
  `ResponsiveDisplay_ProgressBarStyleDeterminesItsMinimumWidth` still pass. A style `Loaded` handler was not
  tested directly because `Loaded` requires a presentation source, which the test layout does not create.

### #3 [P2] Custom item template insets can still make root commands unreachable [Resolved]

- **Status** — Resolved. Repository review #20.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:201-211` and
  `:248-254`.
- **Problem and impact** — The final stage budgets the entire scroll viewport for the row columns.
  A supported `OperationItemsTemplate` can add a horizontal margin inside that viewport. That inset
  reduces the room available to the row without reducing the assigned name-column width. The action
  can be clipped at widths where the documented 150 DIP floor leaves room.
- **Evidence** — At a 320 DIP control width with horizontal scrolling disabled, a custom
  `ItemsControl` template with zero margin put Cancel's right edge at about 303 DIP and its
  center passed hit testing. Adding a 75 DIP left margin left the name width at about 153 DIP,
  moved Cancel's right edge to about 378 DIP and its center beyond the viewport, and made the center
  fail hit testing. The same command column hosts Remove in failed root rows.
- **Suggested resolution** — Size the row using the viewport space actually available to it, including
  any item template insets, or give root actions a way to flow within the row's own layout constraint.
- **Verification** — Exercise both Cancel and Remove in a 320 DIP host with a padded or margined
  custom items template and horizontal scrolling disabled. Verify the buttons fit and accept input.
- **Resolution** — The template names each operation row grid `_OperationRowGrid`. `OperatorControl` finds the
  first visible root row and measures its horizontal inset: its left offset in the scroll content, plus, at each
  level up to the content, the space a parent keeps beside the layout slot it offers the child and the child's
  right margin. Slots are used because aligned containers, such as default `ListBoxItem` presenters, shrink to
  their content. The inset is subtracted from the viewport for stage selection, the final-stage name width, and
  the inline maximum width (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:154`, `:170`,
  and `:284`). The `OperationDisplay` remarks and package README describe the available width.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_NarrowViewportKeepsCommandsReachable` now runs
  with no inset, a 75 DIP left margin, a 30 DIP padded and 2 DIP bordered container, and a default `ListBox`.
  Before the fix the margin and border cases failed (Cancel's right edge at 377.7 and 334.7 DIP in a 303.7 DIP
  viewport). With the inset disabled temporarily, the `ListBox` case also failed. All four pass after the fix:
  Cancel and Remove fit inside the viewport and hit testing at their centers reaches each button. Child rows,
  which have no commands, still gain the inset again at each nesting level, as in Default mode.
