Three P2 findings, all resolved. A running root's Cancel button can be clipped when an items template's inset changes
after layout or when root rows have different insets. The shared width can also leave nested detail text wider

## Findings

### #1 [P2] Changing an items template inset can leave Cancel clipped until resize [Resolved]

- **Status** — Resolved. Repository review #21.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:211-216` and `:282-297`.
- **Problem and impact** — Responsive sizing reads the row inset when the outer scroll viewer reports a change.
  A template can change its margin with the same scroll extent, offset, and viewport. The control keeps its old
  name-column width, which can push Cancel out of reach when horizontal scrolling is disabled.
- **Evidence** — A .NET 10 WPF probe laid out a running root in a 320 DIP control. Setting the realized
  `ItemsControl.Margin` from zero to `75,0,0,0` moved the row 75 DIP, and `ScrollChanged` fired zero times.
  The viewport stayed at 302.67 DIP and the name stayed at 152.67 DIP. The Cancel center moved from 252.67
  to 327.67 DIP and visual hit testing missed the button. Widening the control by 1 DIP caused a recalculation
  and restored the hit.
- **Suggested resolution** — Derive the width during row layout, or invalidate responsive sizing when the actual
  inset changes. Compare the measured inset before updating shared column widths to avoid redundant layout.
- **Verification** — Change a bound or dynamic-resource margin at a fixed viewport with horizontal scrolling
  disabled. Verify Cancel and Remove remain fully inside the viewport and hit-testable through both changes.
- **Resolution** — In Responsive mode the control subscribes to `LayoutUpdated` and, after each layout pass,
  remeasures the root-row inset. It reevaluates the display stage only when the inset differs from the value
  last applied, so the extra pass settles at once
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:212`, `:330`, and `:439`). The
  subscription is removed when the display returns to Default.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_InsetChangeAtFixedWidthKeepsCommandsReachable`
  changes a dynamic-resource `ItemsControl` margin from zero to `75,0,0,0` and back at a fixed 320 DIP width
  with horizontal scrolling disabled. Before the fix, Cancel and Remove ended at 377.67 DIP in a 303.67 DIP
  viewport and failed hit testing after the first change. After it, both buttons fit and pass hit testing
  through both changes.

### #2 [P2] Sizing from the first root row leaves other rows too wide [Resolved]

- **Status** — Resolved. Repository review #22.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:155-186` and `:288-291`,
  with `source/Brows.Operations.Windows/Resources/Styles.xaml:76-81`.
- **Problem and impact** — The control stops at the first visible root row and applies that row's width to the
  shared columns and to every inline details grid. A later root can have a larger inset through its item
  container style. A child can also inherit another inset because the template is reused at each level.
  An inset root can lose access to its command, and long child details can create horizontal scrolling.
- **Evidence** — In a 320 DIP control with scrolling disabled, an item-container trigger gave the second
  running root a 75 DIP left margin and the first root no margin. Both name columns measured 152.67 DIP in
  a 302.67 DIP viewport. The first Cancel center hit at 252.67 DIP. The second missed at 327.67 DIP. In a
  separate 600 DIP layout, applying 30 DIP margins on both sides at every level put a child's long inline
  Data into an extent of 635.15 DIP for a 582.67 DIP viewport, producing 52.48 DIP of horizontal scrolling.
- **Suggested resolution** — Use the tightest available root width for shared command-bearing columns and
  give inline content a width based on its own row's cumulative inset.
- **Verification** — Show two roots with different insets and verify both commands are hit-testable in
  either order. Add a child with long Data beneath a padded root and verify the text wraps within the viewport.
- **Resolution** — The shared columns now use the largest inset among all visible root rows. The search skips
  child operations, because only roots hold commands (`OperatorControl.cs:187`). Inline values are no longer
  capped by one control-wide width. Each row's inline values are hosted in an internal `OperationInlinePanel`
  (`source/Brows.Operations.Windows/Windows/Controls/OperationInlinePanel.cs` and
  `source/Brows.Operations.Windows/Resources/Styles.xaml:78-198`). The panel limits its content to the viewport
  less its own row's inset (`OperatorControl.cs:334` and `:392`), checks its position once after layout,
  and measures again only if that inset changed.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_DifferentRootInsetsKeepCommandsReachable` gives
  the second root a 75 DIP left margin through an item-container trigger, with either root first. Before the
  fix, the inset root's button ended at 377.67 DIP in a 303.67 DIP viewport in both orders; after it, both
  buttons fit and pass hit testing. `ResponsiveDisplay_NestedInlineValuesWrapWithinTheViewport` reproduces the
  600 DIP case with 30 DIP margins on both sides at every level. It failed before the fix with 52.48 DIP of
  horizontal scrolling and passes after it: no horizontal scrolling, the child's Data wraps, and its right edge
  is within the viewport.

### #3 [P2] Responsive sizing ignores a progress bar style's explicit width [Resolved]

- **Status** — Resolved. Repository review #23.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:114-120` and `:145-152`.
- **Problem and impact** — The probe uses the style's `MinWidth` and margins. If the style sets `Width`
  alone, the stage calculation still budgets the 100 DIP fallback and may keep the bar visible when the
  columns overflow. With default scrolling, the rightmost command moves off-screen.
- **Evidence** — A constant `Width=300` setter on `OperationProgressBarStyle` left the bar visible in a
  1,232.67 DIP viewport. The real bar measured 300 DIP, the scroll extent reached 1,350 DIP, and the
  Cancel center landed at 1,300 DIP. The style uses a constant size available to the probe.
- **Suggested resolution** — Include the probe's explicit width when determining the bar's effective
  horizontal requirement, applying its width constraints and margins. Reevaluate when the width changes.
- **Verification** — Use a fixed-width style and resize across the resulting threshold. Verify the bar
  collapses before horizontal overflow and returns after there is room.
- **Resolution** — The probe's `Width` and `MaxWidth` are now bound with its `MinWidth` and `Margin`, and changes
  to any of them reevaluate the stage (`OperatorControl.cs:53` and `:85`). The required width resolves as WPF
  layout does: the explicit width, or the minimum width with the 100 DIP fallback, limited by the maximum width,
  which yields to the minimum, plus horizontal margins (`OperatorControl.cs:142`). The property remarks and the
  package README describe this.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_ProgressBarStyleWidthDeterminesWhenItCollapses`
  failed before the fix for a `Width=300` style at 1,300 DIP (bar visible, 67.33 DIP scrollable width) and passes
  after it. The same test confirms the bar stays visible at 1,500 DIP and when `MaxWidth=150` limits it at 1,300 DIP,
  each without horizontal scrolling.
