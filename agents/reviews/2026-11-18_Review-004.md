## Findings

### #1 [P2] Right-aligned operation lists stay collapsed after widening [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:230`
  and `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:330-336`.
- **Problem and impact** — A custom `OperationItemsTemplate` can right-align its `ItemsControl`. The width
  calculation subtracts the row's current left offset as a fixed inset. As the viewport grows, right
  alignment moves the narrow row farther right by the same amount. The control continues to see only the
  old row width, so the headers stay hidden, the name stays narrow, and the progress bar stays collapsed.
- **Evidence** — A WPF probe with an `ItemsControl` bound to the supplied collection and
  `HorizontalAlignment="Right"` narrowed the control to 320 DIP, then widened it to 1,400 and 2,600 DIP.
  The row stayed at 302.67 DIP wide and in the final stage. Its left offset grew from zero to 1,080
  and 2,280 DIP respectively. Stretch alignment restored the full stage at 1,400 DIP.
- **Suggested resolution** — Base stage selection on the width offered to the list or row before alignment.
  Subtract horizontal space reserved by the template, such as margins and padding, independently of the
  space created by aligning the current row.
- **Verification** — Narrow a right-aligned list until all details are inline. Widen it past the full
  layout threshold and verify that the original name width, headers, and progress bar return.
- **Resolution** — `OperationRowInset` no longer takes the left inset from the row's translated position.
  At each level up to the scroll viewer's content it now adds the space a parent keeps on either side of the
  child's layout slot, plus the child's left and right margins
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:223-243`). Layout slots precede
  alignment, so moving a row within its slot no longer counts as inset, while margins, padding, borders, and
  slot offsets still do. Inline panels share this calculation through `InlineInset`, so their wrap width is
  corrected as well.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_AlignedItemsRestoreColumnsWhenWidened`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1251`) narrows a list to
  320 DIP and widens it to 1,400 DIP. Before the fix, the `Right` case failed: all five values stayed inline,
  the progress bar and headers stayed collapsed, and the name column stayed 152.67 DIP wide. The `Center`
  case already passed because its inset shrinks on each pass. Both cases pass after the fix, as do the
  existing inset tests for margins, padded borders, list boxes, differing root insets, and nested inline values.

### #2 [P2] Inline text keeps a stale wrap width after an inset change [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperationInlinePanel.cs:27-37`
  and `source/Brows.Operations.Windows/Windows/Controls/OperationInlinePanel.cs:64-69`.
- **Problem and impact** — The inline panel checks its measured inset only after it has already measured.
  A change to an ancestor's margin can move the panel during arrange at the same scroll viewport width.
  If the panel receives the same measure constraint, it keeps its previous wrapping width. Inline
  values can then extend past the viewport and require horizontal scrolling until a resize.
- **Evidence** — At a 600 DIP control width with the default scroll style and long inline Data, the
  viewport was 582.67 DIP wide and the text ended at 574.77 DIP. Setting a 100 DIP left margin on
  the live `ItemsControl` kept the viewport width and text height constant and moved the text's
  right edge to 674.77 DIP, creating 92.10 DIP of horizontal overflow. Widening the control by
  one DIP caused the text to wrap onto another line and eliminated the overflow.
- **Suggested resolution** — Recheck the panel's inset when its arranged position can change, even if
  its measure constraint is cached. Invalidate measure when the available inline width changes.
- **Verification** — Add and remove a margin at a fixed viewport width while the final stage stays
  active. Confirm the inline text reflows on both changes and its right edge stays inside the viewport.
- **Resolution** — `OperationInlinePanel` keeps checking its inset after each layout pass while it is
  limited to a viewport, and invalidates its measure only when the inset changes
  (`source/Brows.Operations.Windows/Windows/Controls/OperationInlinePanel.cs:27-43`). The check stops when the
  panel has no `OperatorControl` ancestor or its viewport width is unbounded, as in Default mode, and resumes
  on the panel's next measure.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_InlineValuesRewrapWhenInsetChangesAtFixedWidth`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1289`) keeps a 600 DIP control
  in the final stage with long inline data and changes a dynamic items-template margin from zero to 100 DIP and
  back. Before the fix, the text kept its height and ended 70.19 DIP past the viewport, with an equal scrollable
  width. After the fix it wraps onto more lines inside the viewport with no horizontal scrolling, and returns to
  its original height when the margin is removed.

### #3 [P2] Progress bars with wide control templates overflow before collapsing [Accepted]

- **Status** — Accepted as a documented limitation.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:142-154`
  and `source/Brows.Operations.Windows/Resources/Styles.xaml:327-333`.
- **Problem and impact** — The width calculation uses the progress bar's outer width properties and
  margins. A progress bar template can require more space through its own content, leaving those
  properties at their defaults. Responsive mode can keep the bar visible and add horizontal
  scrolling even though the remaining columns fit without it.
- **Evidence** — A probe assigned an `OperationProgressBarStyle` with a template containing a
  `Border MinWidth="300"`. The live bar's desired width was 300 DIP and its own `MinWidth` was zero.
  At a 1,300 DIP control width, the viewport was 1,282.67 DIP, the bar remained visible, and the scroll
  extent was 1,350 DIP. Adding the same minimum as a setter on the progress bar style collapsed the
  bar and eliminated the overflow. The template's requirement was constant across operations.
- **Suggested resolution** — Include the styled template's measured horizontal requirement in the
  collapse threshold, accounting for width constraints and margins. Setting `MinWidth` on the bar
  style itself works around the issue for a template with a known minimum.
- **Verification** — Use a template with a fixed internal minimum and leave the bar's width properties
  unset. Verify the bar collapses before the extent exceeds the viewport and returns when it fits.
- **Not changed** — The probe progress bar sits in a collapsed host, so its template is never applied or
  measured. Detecting template content would require the probe to take part in layout and the control to
  observe size changes inside the template. That is the trade-off declined for row-specific sizing in
  [Review 002](2026-11-18_Review-002.md) issue #2. The standard WPF themes set no internal minimum width, and a
  template with a known minimum can declare it as `MinWidth` on `OperationProgressBarStyle`, which the
  threshold already honors.
- **Documentation** — The `OperationDisplay` remarks
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:466-468`) and the package README
  (`source/Brows.Operations.Windows/README.md:62-63`) now state that space required inside the progress bar's
  control template is not detected and that such a minimum should also be set as `MinWidth` on the style.
