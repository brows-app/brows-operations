## Summary

Seven confirmed findings (one P1, two P2, four P3). Automatic vertical scrolling can keep responsive layout
from settling. Two custom item layouts put a root command out of reach. Extreme insets and custom header
templates expose two additional layout defects. The new Claude workflows conflict with repository conventions,

### #1 [P1] Automatic vertical scrolling can make responsive layout oscillate [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:254-259` and
  `:331-341`. The Data-inline stage hides the header cells at
  `source/Brows.Operations.Windows/Resources/Styles.xaml:599-602`.
- **Problem and impact** — Stage selection uses the viewport width after the vertical scrollbar takes its
  space. A stage change can also change whether the content fits vertically. With automatic vertical
  scrolling, the scrollbar can appear and disappear repeatedly at a breakpoint. The dispatcher keeps doing
  layout and the control cannot settle at a fixed size. The sample scroll style also enables automatic
  vertical scrolling (`samples/Brows.Operations.Sample/Resources/OperationsTheme.xaml:197`).
- **Evidence** — A .NET 10 WPF probe used a single failed root with short Data and error text, the stock
  operation templates, and automatic horizontal and vertical scrollbars. At a control size of 655 by 120 DIP,
  the 655 DIP viewport kept the Data column and its header, leaving about 94.04 DIP of viewport height for
  99.76 DIP of rows. The vertical scrollbar reduced the width to 637.67 DIP and put Data inline. Hiding the
  header let 115.72 DIP of rows fit inside 120 DIP, removing the scrollbar and restoring the previous stage.
  The probe stopped the reproduction after observing 31 successive width changes between these two values.
  A running root with a 42 DIP tall progress bar reproduced the same loop at the progress-bar breakpoint.
- **Suggested resolution** — Make the stage decision stable when the stage itself can change scrollbar
  visibility. For example, reserve the automatic scrollbar's gutter when evaluating stage widths, or keep
  the narrower stage until widening provides enough room with the gutter present.
- **Verification** — Arrange the failed root near the Data-inline breakpoint with automatic vertical
  scrolling. Assert that viewport and stage changes settle at a fixed size and that resizing across the
  surrounding widths still restores the columns.
- **Resolution** — While the list's vertical scrollbar is `Auto` and hidden, `ReservedViewportWidth`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:271-291`) subtracts the larger of the system
  scrollbar width and the width last observed while the scrollbar was visible. `UpdateDisplayStage`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:410-431`) uses that reserved width for stage
  selection, the narrowed Name column, and the inline wrapping width, so showing or hiding the scrollbar no longer
  changes any of them. Root rows use the unreserved viewport through the new internal `RowViewportWidth`, because a
  row's width does not change whether the rows fit vertically.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_SettlesWithAutomaticVerticalScrolling`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1348`) uses automatic horizontal
  and vertical scrolling at a width whose viewport straddles a breakpoint with and without the scrollbar, sweeps the
  height from 60 to 160 DIP, and stops the layout after 20 viewport-width changes. Before the fix, the failed root
  at 660 DIP (data breakpoint) oscillated at 116 DIP tall, and the running root with a 42 DIP progress bar at 1,160
  DIP (progress-bar breakpoint) at 60 DIP. Both settle at every height after the fix and restore every column at
  1,400 DIP.

### #2 [P2] A deeper operation can push root commands beyond the viewport [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Resources/Styles.xaml:243-252` and `:308-324`.
  The shared Name budget is set at
  `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:291-301`.
- **Problem and impact** — A descendant row can widen the scroll extent because the same items template
  adds an inset at every depth. The root row then stretches to the resulting extent. Its empty status
  column still takes the remaining width after the progress bar collapses, so it moves the command
  column to the right of the viewport even when the root had enough space for the command.
- **Evidence** — With the default scroll style and an `ItemsControl` template with `Margin="35,0"`, a failed
  grandchild with short Data made a 400 DIP control enter the Data-inline stage. The viewport was 382.67 DIP
  and the scroll extent was 522.67 DIP. The empty root status column took 140 DIP, and Remove ended at
  487.67 DIP. Hit testing its center missed the button. The root alone had 312.67 DIP available after
  its margins, above the documented 150 DIP minimum for the Depth and Command columns.
- **Suggested resolution** — Give the status column zero width when the responsive stage has hidden its
  content, or constrain the command-bearing row to its viewport budget independently of the descendant extent.
- **Verification** — Use an inset template with a root, child, and grandchild under the default scroll style.
  Check both root commands in their respective running and failed states, including pointer hit testing with
  horizontal scroll at its starting position.
- **Resolution** — Each operation's row grid is now wrapped in an `OperationInlinePanel`
  (`source/Brows.Operations.Windows/Resources/Styles.xaml:221-432`). For a root operation, its style binds
  `ViewportWidth` to `RowViewportWidth`, so the panel limits the row to the viewport less the row's own inset and
  width limits. Deeper rows remain unlimited and still widen the scroll extent, which keeps them scrollable. The
  root row's empty status column therefore can no longer stretch to an extent created by descendants, in any stage.
  The inset calculation does not count the space this panel leaves beside the row it limits
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:237-269`). The panel's viewport binding
  moved from its constructor to XAML so that each use chooses its viewport
  (`source/Brows.Operations.Windows/Windows/Controls/OperationInlinePanel.cs` and
  `source/Brows.Operations.Windows/Resources/Styles.xaml:78-80`).
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_DeeperOperationsKeepRootCommandsReachable`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1410`) uses a `Margin="35,0"`
  items template, a root with a child and a failed grandchild, and a second root, under the default scroll style at
  400 DIP. Before the fix, Cancel and Remove ended at 487.67 DIP in a 383.67 DIP viewport and failed hit testing,
  both with the deep root running and with it failed. Both cases pass after the fix while the extent still scrolls
  horizontally.

### #3 [P2] A constrained items template can leave the command permanently clipped [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:223-242` and `:331-337`.
- **Problem and impact** — Inset calculation uses each ancestor's layout slot before alignment. That is
  appropriate for a naturally sized, aligned list, but it also ignores explicit `Width` and `MaxWidth`
  constraints on the realized item list. A wide outer viewport keeps the control in its full column
  layout even when the list inside it has room only for the narrow layout. The command can be clipped
  inside the list without a horizontal scrollbar to reach it.
- **Evidence** — An `OperationItemsTemplate` containing `<ItemsControl ItemsSource="{Binding}" Width="320"/>`
  received a 1,382.67 DIP layout slot and arranged at 320 DIP inside a 1,400 DIP control. The measured
  inset was zero, all columns stayed in place, and a failed root's Remove button failed hit testing.
  The scroll extent was only 320 DIP. Setting `MaxWidth="320"` instead produced the same failure.
- **Suggested resolution** — Account for the effective explicit width caps along the row's layout path
  when computing available width. Preserve widening for lists that size to their content solely because
  of alignment.
- **Verification** — In a wide host, constrain the items template with `Width` and then `MaxWidth`. Confirm
  that the stage follows the list's available width and Remove is inside that list and hit-testable.
- **Resolution** — The row inset calculation became `OperationRowWidth`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:237-269`), which returns the width available
  to a row. While walking up to the scroll viewer's content, it also limits that width at each element by the
  element's effective `Width` or `MaxWidth`, respecting `MinWidth`, less the inset accumulated inside that element.
  Alignment still does not count as inset, so lists that are narrow only because of alignment keep widening. The
  stage search (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:196-215`) now takes the
  narrowest root row, and inline panels use the same width through `AvailableRowWidth`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:489-493`).
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_WidthLimitedItemsKeepCommandsReachable`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1456`) limits the items list to
  320 DIP with `Width` and then with `MaxWidth` in a 1,400 DIP control. Before the fix, neither case entered the
  Data-inline stage. After the fix, both enter it, and both root commands are inside the viewport and hit-testable.

### #4 [P3] An inset that consumes the viewport leaves responsive state stale [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:331-342`.
- **Problem and impact** — The positive-available-width guard skips the entire update when the viewport
  exists but the root inset consumes it. The display stage, Name width, and inline viewport retain values
  from earlier layouts. The same final size can show different columns and require different amounts of
  horizontal scrolling depending on the resize path.
- **Evidence** — With a 400 DIP trailing items margin and a single failed root, resizing from 1,400 DIP
  directly to 300 DIP kept Data and Progress in columns and left a 1,250 DIP extent. Resizing through
  600 DIP before returning to 300 DIP kept Data inline, retained a 32.67 DIP Name column, and left an
  800 DIP extent. Both 300 DIP layouts reported a 282.67 DIP viewport and a 400 DIP inset.
- **Suggested resolution** — Distinguish a viewport awaiting layout from a measured viewport whose
  available row width is zero. For the latter, update the inline viewport and use zero for stage selection
  and Name sizing.
- **Verification** — Compare the display at widths equal to and smaller than the inset after narrowing
  from different stages. Confirm identical stage flags and column widths at the same measured width.
- **Resolution** — `UpdateDisplayStage`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:410-431`) now returns early only while the
  viewport has not been measured. A measured viewport whose available row width is zero or less updates the inline
  viewport and uses zero for stage selection and Name sizing.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_InsetWiderThanViewportIsIndependentOfResizePath`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1487`) gives a failed root a 400
  DIP trailing items margin. It resizes one control from 1,400 to 300 DIP and another through 600 DIP. Before the
  fix, the direct path kept Data and Progress in columns with a 967.33 DIP scrollable width, while the stepped path
  was in the Data-inline stage with a 32.67 DIP Name column. After the fix, both reach the Data-inline stage with a
  zero-width Name column and identical stage flags, column widths, and scrollable width.

### #5 [P3] Applying a custom template resets its local header widths in Default mode [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:304-309` and
  `:1090-1100`.
- **Problem and impact** — Applying a template always calls `ApplyHeaderColumnWidths`. In Default mode every
  column takes the branch that clears its local Width, even on first application. Template-supplied local
  widths or bindings on columns created in code can be lost during an upgrade.
- **Evidence** — A probe used a custom `PART_OperationHeaderGrid` that constructed columns with local widths of
  120 and 200 DIP. After `ApplyTemplate` on a new Default-mode control, both widths were `1*`. The baseline
  template hook only assigned the header's render transform and bound its minimum width when a scroll viewer
  was present. It did not mutate column definitions.
- **Suggested resolution** — Leave untouched columns alone and preserve the original value source for any
  temporary responsive override so switching to Default can restore it.
- **Verification** — Apply a custom header template with local Width values and a Width binding in Default
  mode. Exercise a Responsive-to-Default round trip and verify that all values and the binding survive.
- **Resolution** — Header columns are now changed only while the responsive layout overrides them
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:332-396`). The first override saves the
  column's local value, such as a binding, and its width. Ending the override restores that binding or value, or
  clears the property when there was none, so template values return as before. Columns that were never overridden
  are left untouched, so applying a template in Default mode no longer modifies them. Stage widths read an
  unmodified column's current width.
- **Fix verification** — `OperatorControlTests.DefaultDisplay_PreservesTemplateHeaderColumnWidths`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1526`) applies a template whose
  header grid creates columns in code with a local 120 DIP width and a 200 DIP width binding. Before the fix, both
  widths became `*` and the binding was lost.
  `OperatorControlTests.ResponsiveDisplay_RestoresHeaderColumnWidthBindingsWhenDisabled`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1546`) binds the stock Data header
  column to 300 DIP, collapses it in Responsive mode, and returns to Default. Before the fix, the binding was lost
  and the width reverted to 250 DIP. Both pass after the fix.
