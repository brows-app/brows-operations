### #1 [P1] A narrower custom vertical scrollbar can still cause a layout loop [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:279-290`.
- **Problem and impact** — With automatic vertical scrolling, the stage calculation uses the actual viewport
  when the bar is visible and reserves at least the system scrollbar width when it is hidden. If a custom bar
  is narrower, the effective width used to select a stage can shrink when the bar disappears. The narrower
  stage can then add enough height to bring the bar back. The dispatcher repeatedly lays out the same control
  at a fixed size. The package README promises stable layout as an automatic scrollbar appears and disappears
  (`source/Brows.Operations.Windows/README.md:55-58`).
- **Evidence** — A .NET 10 WPF probe used the stock operation templates, four failed roots with short Data
  and error text, and an `OperationScrollViewerStyle` with a 5 DIP automatic vertical scrollbar. At a control
  size of 660 by 430 DIP, the visible bar left 655 DIP for columns. The Data column and header were present,
  and 399.04 DIP of rows fit into the remaining 404.04 DIP of viewport height. When the bar disappeared, the
  algorithm budgeted 642.67 DIP after reserving the 17.33 DIP system width. Data moved inline and row height
  grew to 462.88 DIP, bringing the bar back. The widths repeatedly alternated between 655 and 660 DIP until
  the probe switched to Default mode at its event limit. The stock-scrollbar tests use a style with the
  theme's existing scrollbar template
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1361-1366`).
- **Suggested resolution** — Evaluate responsive stage and wrapping widths against the same effective gutter
  whether the scrollbar is visible or hidden. Use the actual space consumed by the active template when known,
  including values below the system width, and make the fallback stable across visibility changes.
- **Verification** — Arrange multiple failed roots near the Data breakpoint with an automatic scrollbar
  narrower than the system default. Assert that both the width and stage settle and stay stable at a fixed size.
- **Resolution** — `ReservedViewportWidth`
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:295-326`) now reserves exactly the width the
  vertical scrollbar takes instead of at least the system width. A stage change can make rows taller as well as
  shorter, so any difference between the reserved and actual width can toggle the scrollbar. The reserved width is
  the scrollbar's actual width plus margins last seen while it was visible, then its declared `Width` or `MinWidth`
  plus margins, and the system width only when neither is known. The remembered width is discarded when the scroll
  viewer's template supplies a different scrollbar.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_SettlesWithAutomaticVerticalScrolling`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1353`) gained a case with four
  failed roots, a 5 DIP automatic vertical scrollbar set by an implicit style, and a 660 DIP control swept from 380
  to 480 DIP tall. Before the fix, the viewport width kept changing at 426 DIP tall until the test's 20-change limit
  switched the control to Default mode. After the fix it settles at every height and restores every column at 1,400
  DIP. The two existing theme-scrollbar cases still pass.

### #2 [P2] Responsive column overrides change or disconnect bound header widths [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:332-359`.
- **Problem and impact** — Responsive layout saves each header column's local value and then assigns
  `column.Width`. When a width is bound two-way, that temporary value is written to the binding source.
  Restoring the binding cannot recover the consumer's original width. A one-way binding is instead removed
  while the column is collapsed. The stage calculation uses its cached old width, so it can leave columns
  inline even after the source widths shrink enough to fit.
- **Evidence** — At a 1,020 DIP control width, collapsing the Rate column changed its two-way source from
  100 to 0 DIP. Returning to Default reattached the binding and left the source and column at zero. In a
  separate run with two one-way bindings, shrinking Rate and Average from 100 to 65 DIP each at the same
  1,002.67 DIP viewport left both inline. Widening the control once restored the bindings. On returning to
  the original viewport, both columns fit and stayed visible. The existing restore test uses a constant
  source and checks only that the binding returns
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1546-1568`).
- **Suggested resolution** — Keep the consumer's live width as an input to the stage calculation and apply
  responsive hiding or narrowing through a layout value that cannot write to that source. Reevaluate the stage
  when the declared width changes, including while its column is collapsed.
- **Verification** — Collapse and restore a column with a two-way width binding and assert the source value
  stays intact. Change the source widths of collapsed one-way columns at a fixed viewport and verify those
  columns reappear when they fit.
- **Resolution** — Before the responsive layout first overrides a header column bound by the consumer, it clears the
  binding from `Width` without writing to its source and attaches it to a private attached property,
  `HeaderColumnDeclaredWidth` (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:146-164`).
  Assigning the override therefore cannot reach a two-way source, and the binding keeps tracking its source while
  the column is overridden. `DeclaredHeaderColumnWidth` and the override helpers
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:367-460`) read that live width for stage
  selection and Name sizing, and restoring the column moves the binding back to `Width`. A change to the attached
  width reevaluates the stage, and the layout handler
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:247-259`) also reevaluates it when a
  declared header width differs from the one last used. Overriding `MaxWidth` instead was tried and rejected: header
  columns in a shared size group keep their width despite `MaxWidth`.
- **Fix verification** — `OperatorControlTests.ResponsiveDisplay_KeepsTwoWayHeaderColumnWidthSources`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1598`) binds the Rate header width
  two-way to a 100 DIP source and collapses it at 1,020 DIP. Before the fix, the source became zero and stayed zero
  after returning to Default. After the fix, the column collapses while the source stays at 100 DIP, and the column
  returns to 100 DIP with its binding. `OperatorControlTests.ResponsiveDisplay_FollowsBoundHeaderColumnWidthChanges`
  (`tests/Brows.Operations.Windows.Tests/Windows/Controls/OperatorControlTests.cs:1633`) binds Rate and Average
  one-way, collapses them at 1,020 DIP, and shrinks both sources to 65 DIP at the same size. Before the fix, both
  stayed collapsed at zero width. After the fix, both reappear at 65 DIP in the progress-bar-collapsed stage without
  horizontal scrolling. The Review 005 header-width tests still pass.
