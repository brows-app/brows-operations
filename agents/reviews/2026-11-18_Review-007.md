## Findings

### #1 [P1] An overlaid automatic scrollbar can cause a layout loop [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:309-324`.
- **Problem and impact** — When the vertical scrollbar is visible, responsive layout assumes its actual
  width plus margins is already deducted from the viewport. A custom `OperationScrollViewerStyle` can put
  the scrollbar over the content so it takes no space from the viewport. Hiding it then causes the code
  to subtract its width anyway, changing the stage and the amount of vertical space the rows need.
  The scrollbar can keep reappearing and disappearing at a fixed control size.
- **Evidence** — A .NET 10 WPF probe used four failed roots with short Data and error text and a right-aligned
  12 DIP vertical scrollbar in the same grid cell as the scroll content presenter. At 655 by 430 DIP the
  viewport remained 655 DIP wide. With the bar visible, Data stayed in columns. About 399.04 DIP of rows
  fit into the 404.04 DIP left below the header, so the bar disappeared. The control then reserved 12 DIP
  for the hidden bar, budgeting 643 DIP. Data moved inline and the rows grew to 462.88 DIP, bringing the bar
  back. The probe observed 24 alternating extent-height changes before switching to Default to stop the loop.
- **Suggested resolution** — Use the actual gutter consumed by the scroll template, which can be zero for
  an overlay, or use a layout width independent of scrollbar visibility for stage selection and inline
  wrapping.
- **Verification** — Place an automatic vertical scrollbar over the content, arrange the control near the
  Data breakpoint, and verify that stage and scrollbar visibility settle at a fixed size.
- **Resolution** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:278` measures the
  visible scrollbar's overlap with the scroll content presenter and reserves it in the viewport calculation.
  Stage selection, inline details, and root rows use the same width budget.
- **Fix verification** — `ResponsiveDisplay_SettlesWithOverlaidVerticalScrollbar` hit its 20-change guard
  on the original code. After the fix, layout settles at 655 by 430 DIP and stays in Responsive mode.

### #2 [P2] Moving a OneWayToSource header binding can overwrite its source [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:151-162` and `:392-413`.
- **Problem and impact** — Responsive layout reattaches the original binding to a private property with a
  default width of `1*`. A `OneWayToSource` width binding publishes the private property's current value
  to the source. It then publishes from a freshly attached binding when the column width is restored.
  A consumer tracking the header width can receive the private property's value and lose the original
  pixel width even after returning to Default.
- **Evidence** — A probe bound the Rate column's Width to a source column using
  `BindingMode.OneWayToSource`, then used `SetCurrentValue` to set the bound Rate width to 100 DIP.
  At 1,400 DIP both values were 100. Narrowing to 1,020 DIP caused the override path to run.
  After layout, both reported `1*`. Switching to Default and widening to 1,400 DIP left both at `1*`
  with the binding attached. The new source-preservation test covers TwoWay, which reads the source when
  the private binding is attached.
- **Suggested resolution** — Keep the original width and its output binding separate from temporary layout
  values. If moving a binding remains necessary, preserve the consumer's current width and handle
  source-only bindings without publishing an internal value.
- **Verification** — Set a pixel width on a header column with a `OneWayToSource` binding, narrow enough
  to override it, then return to Default. Verify that the output source keeps the pixel width and the
  original column width and binding are restored.
- **Resolution** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:391` applies the
  temporary layout width through a paused WPF animation. The original Width binding stays attached, and
  removing the override restores the consumer's effective width.
- **Fix verification** — `ResponsiveDisplay_KeepsHeaderColumnWidthSources(OneWayToSource)` originally
  changed the source from 100 DIP to `1*`. After the fix, both the source-only and two-way cases keep
  the source at 100 DIP and keep the binding attached while collapsed and after restoration.

### #3 [P3] Collapsed header widths ignore updates to dynamic resources [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:367-373` and `:392-399`.
- **Problem and impact** — The live declared-width path covers binding expressions. Responsive layout
  replaces a dynamic Width resource and uses its captured value until the override ends. A theme or
  runtime resource change that makes collapsed columns fit can leave the fields inline until the control
  is widened.
- **Evidence** — A probe set Rate and Average Width using the same dynamic resource at 100 DIP per
  column. In a 1,002.67 DIP viewport both were inline. Changing the resource to 65 DIP per column left
  them inline at that viewport. Widening restored the resources. Returning to the original viewport
  kept both columns visible at 65 DIP, with an observed content extent of 980 DIP.
- **Suggested resolution** — Keep resource-backed declared widths live while calculating the stage and
  apply responsive overrides to a separate layout value. Reevaluate when the resource changes while the
  headers are collapsed.
- **Verification** — Reduce the dynamic resource at a fixed viewport while both columns are inline.
  Verify that the columns reappear when they fit and that future resource updates continue to apply.
- **Resolution** — The temporary animation leaves the Width resource active. The control reads the
  unanimated width for stage selection and schedules reevaluation when WPF evaluates the override
  (`source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:358` and `:374`).
- **Fix verification** — `ResponsiveDisplay_FollowsDynamicResourceHeaderColumnWidthChanges` originally
  left both columns at zero after changing the resource from 100 to 65 DIP. After the fix, the columns
  reappear at 65 DIP and collapse again at 100 DIP at the same viewport, without forcing a new layout.
