## Findings

### #1 [P1] Consumer header width animations can keep responsive layout from settling [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:358-362` and
  `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:401-411`.
- **Problem and trigger** — With its responsive override active, the control reads `GetAnimationBaseValue`
  for stage selection. WPF excludes all animations from that value. When the column is restored, the control
  reads `column.Width`, which includes the consumer's animation. A breakpoint between those two widths
  makes the control repeatedly restore and collapse the same columns. [WPF animation base value][animation]
- **Impact** — A fixed-width layout can keep invalidating itself after the consumer's animation has reached a
  constant value. The dispatcher stays busy and the rows cannot settle.
- **Evidence** — A .NET 10 WPF probe set both rate columns to a base width of 65 DIP and attached constant
  100 DIP animations. At a fixed 1,020 DIP viewport with about 1,002.67 DIP available to rows, the two widths
  made the columns fit at 980 DIP or overflow at 1,050 DIP. The scroll extent repeatedly alternated between
  850 and 1,002.67 DIP, and the effective rate widths alternated between 100 and 0 DIP. A guard switched to
  Default after 24 scroll updates to end the loop.
- **Suggested resolution** — Use the same consumer-effective width at every stage. Keep responsive layout
  widths separate or capture the input to the composed responsive animation before it supplies its override.
- **Verification** — Apply constant 100 DIP animations over 65 DIP base values at the breakpoint. Verify
  the rates stay inline, dispatcher layout settles, and returning to Default reveals the consumer animations.
- **Resolution** — `ResponsiveHeaderColumn` uses the input to its composed WPF animation to measure
  the consumer's effective width. It also detects replacement of the consumer animation during collapse.
- **Fix verification** — `ResponsiveDisplay_PreservesAnimatedRateWidths` failed on the reviewed code.
  It now settles with both rates inline, restores both 100 DIP animations when widened, and shows both
  columns at a fixed viewport when new 65 DIP animations replace the old ones.

### #2 [P2] Minimum widths on hidden columns can clip root commands [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:335-345` and
  `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:429-445`.
- **Problem and trigger** — Stage selection counts collapsed columns as zero and the override only sets
  `Width`. A nonzero `MinWidth` on the header definition still contributes to its shared size group,
  so the empty row cells keep taking up width.
- **Impact** — Root Cancel or Remove can be clipped even when enough space exists for the selected responsive
  stage. The row width limit can leave the scroll viewer with zero horizontal scroll range.
- **Evidence** — At a 900 DIP viewport, a .NET 10 WPF probe set `MinWidth=65` on both rate header
  columns before narrowing. The rates moved inline and both header `Width` values became zero, but the
  row still reserved 65 DIP for each rate column. Its Remove button spanned x=880 to x=980, and the
  scroll viewer reported `ScrollableWidth=0`. Hit testing near the button's right edge missed it.
- **Suggested resolution** — Make collapsed shared columns contribute zero to layout, including any minimum
  width, and preserve the original width constraints when the columns are restored. Use the effective
  constraints of the remaining columns to calculate the width budget.
- **Verification** — Set a positive minimum on both rate columns, narrow until both rates move inline, and
  verify that the entire root command is inside the viewport and can be hit-tested. Widen and verify the
  original minimum widths apply again.
- **Resolution** — The responsive override applies and releases Width and MinWidth together. Stage
  selection includes the effective minimum width of each remaining column.
- **Fix verification** — `ResponsiveDisplay_CollapsesRateColumnMinimumWidths` previously measured
  two 65 DIP columns while collapsed. Both now measure zero, the entire Remove button fits, and widening
  restores the 65 DIP minimums and 100 DIP column widths.

### #3 [P2] An always-visible overlaid scrollbar can cover root commands [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:291-305`.
- **Problem and trigger** — The visible-scrollbar branch only measures overlap when
  `VerticalScrollBarVisibility` is `Auto`. A custom scroll template can place a `Visible` scrollbar
  over the content too. The responsive display contract reserves this overlap. [Windows package README][readme]
- **Impact** — Responsive stages can keep columns that exceed the unobstructed width, and the scrollbar can
  intercept clicks meant for the right edge of a root command.
- **Evidence** — A .NET 10 WPF probe arranged four failed roots in a 655 DIP viewport with a 12 DIP
  always-visible scrollbar over the right edge of the scroll content presenter. The width budget remained
  655 DIP and Data stayed in its column. Remove spanned x=555 to x=655. A hit at x=651 inside the button's
  bounds reached the scrollbar, and the scroll viewer reported `ScrollableWidth=0`.
- **Suggested resolution** — Measure overlap whenever a vertical scrollbar is visible. Keep the reservation
  for hidden bars conditional on `Auto`. A visible docked scrollbar should continue to have zero overlap.
- **Verification** — Parameterize the overlaid scrollbar fixture for `Visible` as well as `Auto`. Check
  the stage at the breakpoint and verify the entire root command is reachable.
- **Resolution** — `ReservedViewportWidth` deducts the visible scrollbar's horizontal overlap for
  both automatic and always-visible scrollbars.
- **Fix verification** — `ResponsiveDisplay_SettlesWithVerticalScrollbar(Visible,0)` previously placed
  the right edge of Remove at x=655. The button now ends before the overlaid bar and a hit test
  from the control reaches the button at its right edge.

### #4 [P3] A hidden scrollbar can reserve more than its maximum width [Resolved]

- **Status** — Resolved.
- **Location** — `source/Brows.Operations.Windows/Windows/Controls/OperatorControl.cs:310-316`.
- **Problem and trigger** — Before an automatic scrollbar is visible, the fallback width ignores `MaxWidth`.
  WPF applies that limit when arranging the scrollbar. The first visible arrangement replaces the estimate
  with the measured width, so prior scrolling can change which responsive stage a fixed viewport uses.
  [WPF width precedence][width]
- **Impact** — A fresh control can move values inline prematurely and use extra vertical space.
- **Evidence** — At 670 by 600 DIP, a .NET 10 WPF probe with an overlaid scrollbar configured with
  `Width=30`, `MinWidth=0`, and `MaxWidth=12` initially reserved 30 DIP and moved Data inline.
  Reducing the height to 120 DIP showed the scrollbar at 12 DIP. Returning to 670 by 600 DIP hid the
  scrollbar again, with Data now in its column and a 12 DIP reservation.
- **Suggested resolution** — Apply WPF width precedence to the declared scrollbar sizing before adding the
  margins, and use a measured fallback where the template supplies no explicit effective width.
- **Verification** — Compare the displayed stage and reserved width before and after the scrollbar has been
  visible. Both should match at the original viewport.
- **Resolution** — The hidden scrollbar estimate honors Width, MinWidth, MaxWidth, and horizontal margins.
  It also credits a permanent gutter that the scroll template already reserves beside the presenter.
- **Fix verification** — `ResponsiveDisplay_SettlesWithVerticalScrollbar(Auto,0)` previously moved Data
  inline at 670 DIP. The corrected control keeps Data in its column before and after the scrollbar appears.
  The additional `(Auto,12)` case reproduced double counting a permanent gutter and now passes as well.
